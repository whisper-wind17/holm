# Topic 1 · 首次部署

**可见性：** 仅管理员

## 这篇讲什么

从一台刚装好平台的服务器，到团队能调用第一个 AI 服务，中间有四步。下载与启动所需时间取决于模型大小、网络带宽和运行配置。

## 四步的顺序不能颠倒

1. **确认 GPU 可用。** 在「系统」页看 GPU 列表，结合健康状态和占用情况确认可用资源。被占用或健康信息不可用时，先处理原因并刷新资源，不要绕过部署校验。
2. **部署一个模型实例。** 本地模型有两种来源：从「模型 → 下载模型」下载，或选择「服务器本地目录」登记服务器已有目录。外部目录只读使用，平台不复制、不修改文件，移除登记也不删除源文件。等待校验通过、本地模型就绪后，再进入「部署模型」选择本地模型、GPU 和运行配置。
3. **等待部署完成。** 下载任务与模型实例分别显示进度。**离开这个页面不会中断部署**，你可以去做别的事，稍后从实例详情回来看进度。
4. **发布为 AI 服务。** 实例运行起来之后，它还只是一个内部对象。要让团队用，到「AI 服务」创建服务、绑定运行中的模型实例，并为用户授予访问权限。

## 两个最容易卡住的地方

### 下载期间不占用 GPU

下载任务不预留 GPU。部署向导选择资源后，实际启动前平台会重新检查并原子预留 GPU。这么设计是因为下载一个 32B 模型可能要一小时，让最贵的资源空转一小时不合理。

代价是：**部署到后期有可能要你重新选 GPU**。如果那几张卡在这段时间被别的部署占用了，实例会进入「等待 GPU 资源」。可以选择「等待原 GPU」「重新选择 GPU」或「取消部署」。平台不会静默换卡，也不会因为等待资源重新下载已就绪的文件。

### 显存不足是最常见的失败原因

一个 32B 模型的权重约 65 GB，加上 KV Cache 预留，单张 48 GB 的卡放不下。失败页会给出可尝试的方向：用 2 张同型号卡（TP 2）、降低「上下文长度」、或调高「显存比例」。这些是建议不是保证，因为实际占用还取决于并发量。

## 接下来

部署成功后读「服务发布」。如果部署失败，读「故障排查」的「部署失败」一节。

# Topic 2 · 服务发布

**可见性：** 仅管理员

## 这篇讲什么

模型实例是**运行对象**，AI 服务是**给用户的稳定能力**。两者故意分开：实例可以重启、换配置、甚至换一台卡重建，而服务的名字和API 模型名保持不变，用户的代码不用改。

## 发布一个服务

从「AI 服务 → 创建服务」进入；模型实例的发布操作也会带你到 AI 服务页面。当前创建表单填写以下四项，创建后再设置用户访问权限：

- **描述** —— 帮用户判断该用哪个服务。**不要写模型、显卡或运行参数**，用户看不到也不需要知道。
- **服务名称** —— 用户在页面上看到的名称，可在服务设置中独立修改。
- **API 模型名** —— 用户在 API 请求的 `model` 字段里填的值，也是平台内部的路由标识。全平台唯一。
- **绑定实例** —— 选择运行中的模型实例，作为这个服务的后端。

创建成功后，在服务的访问权限入口或用户详情中授权用户。服务名称用于页面展示，为 2～40 个字符且全平台唯一；首尾空白会自动去除。API 模型名用于 API 调用。

## 发布之后用户还差一步

授权不等于能调用。**每个用户必须自己创建 API 密钥**——你不能代他创建，也看不到他的密钥明文。这是有意的设计：密钥明文只在创建的那一次出现，平台之后只保留前缀和后四位。

所以如果用户说「调不通」，先确认两件事：他被授权了吗？他建了密钥吗？

管理员需要先在用户详情中为自己的账号分配 AI 服务，再从右上角用户菜单进入「个人 API 密钥」。没有服务授权时，该入口隐藏；管理员角色本身不提供服务调用权限。

## 一个服务只有一个后端，一个后端可以有多个服务

你可以把两个服务指向同一个模型实例（例如「文本生成」和「内部问答」共用一个 32B 实例）。这时监控页里有个区别要留意：**推理引擎自身的队列、吞吐和 KV Cache 是实例总量，无法按服务拆分**，界面会标「共享后端」。而 TTFT、TPS、错误率由平台在转发请求时按服务分别统计，可以逐服务比较。

## 改动服务的两个风险点

**切换后端实例**是安全的：平台先做健康校验，再更新路由，校验失败则保留原后端。切换前仍应确认新实例可以提供预期能力。

**修改API 模型名会影响使用旧名称的客户端。** 在 AI 服务详情的“服务设置”中选择“修改API 模型名”，填写新名称并再次输入确认后保存。名称应为 2～64 位小写字母、数字、点、下划线或短横线，且不能与其他服务重名。路由刷新后，仍使用旧名称的脚本和 IDE 插件会收到 `404 model_not_found`，平台不做旧名转发；已开始的调用不会因此中断。请同步修改客户端配置。若提示配置已更新，先刷新当前配置，再重新输入确认名称。

## 停用或删除服务

只想暂停调用时，停用服务即可：配置和历史用量关系保留，用户仍能看到该服务，但显示「不可用」，调用返回 `503 service_disabled`。不再使用时，先停用再删除服务；删除后使用该 API 模型名的调用返回 `404 model_not_found`，模型实例保留。

## 为用户设置调用上限

管理员可在用户详情的「服务权限」中，为每个「用户 × 服务」设置「同时请求」和「每分钟请求」上限；服务详情的「访问权限」修改的是同一份设置。

超过同时请求上限时，请求先排队，最长等待 60 秒。排队已满或等待超时，或超过每分钟请求上限时，返回 `429 rate_limit_exceeded`，并带 `Retry-After`，提示稍后重试。

# Topic 3 · API 接入

**可见性：** 管理员与普通用户

## 这篇讲什么

平台同时提供 OpenAI 兼容接口和 Anthropic 兼容接口（`/v1/messages`），后者可用于 Claude Code 等编程工具。两种接口共用同一 API 密钥和 API 模型名，接入时都需要核对 Base URL、API 模型名和 API 密钥三项配置。

## 你需要三样东西

| 项 | 从哪里拿 |
|---|---|
| Endpoint | 「AI 服务」详情的两行 Endpoint，全平台统一；OpenAI SDK、Cursor 等复制「OpenAI 兼容 Endpoint」，Claude Code 复制「Anthropic 兼容 Endpoint」 |
| API 模型名 | 「AI 服务」的接入指引中 model，每个服务不同 |
| API 密钥 | 你自己创建，见下 |

## 创建 API 密钥

普通用户从「API 密钥 → 创建密钥」进入。三个字段：

- **名称** —— 给自己看的标识，建议写用在哪里（`Kevin-Cursor`、`summary-cron`），日后撤销时不会撤错。
- **允许服务** —— 可选「全部已授权服务（含以后新授权的）」或「指定服务」；指定服务只能从你已获授权的服务中选择。建议**一个用途一个密钥**：某个脚本出问题时可以只撤销它，不影响你的 IDE。
- **有效期** —— 到期后自动失效且**不能续期**，只能新建。

**完整密钥只显示一次。** 创建成功的弹层是唯一一次能看到明文的机会，关闭之后平台只保留前缀和后四位（用来帮你认出是哪一个）。现在就存进受控的密钥管理工具。如果没存下来，只能新建一个并撤销旧的。

弹层里提供「测试调用」：平台用这个密钥向该服务发一个最小请求（`max_tokens=8`），分四段告诉你 Endpoint、鉴权、服务路由、模型响应是否通。这次调用会计入你的用量，但**平台不保存请求和响应正文**。测试只能在弹层里做——关闭之后平台不再持有明文，也就无法替你发起。不要把请求或响应正文粘贴到故障反馈中。

## 把密钥放进环境变量，不要写进代码

平台的示例一律用环境变量占位符，不在示例里注入明文。原因很直接：写进代码的密钥会跟着代码进版本库。

## 常见的三个配置错误

1. **Base URL 后面多加了路径。** OpenAI SDK 使用「OpenAI 兼容 Endpoint」，不要再加 `/chat/completions`；Claude Code 使用「Anthropic 兼容 Endpoint」。
2. **`model` 填了模型的原始名称。** 要填接入指引中 model 那一行的值。
3. **密钥没复制完整。** 应完整复制创建时显示的密钥，包含前缀。

## 第三方工具（Claude Code、Cursor、Cline、Continue）

Claude Code 的 Base URL 使用「Anthropic 兼容 Endpoint」，配置见服务详情的「Claude Code」标签页。Claude Code 的 Base URL 误填成带 `/v1` 的地址也能正常调用。Cursor、Cline、Continue 的 Base URL 使用「OpenAI 兼容 Endpoint」，再填入 API 模型名和 API 密钥。**字段名称和位置以你所用版本为准**——这类工具改版比平台频繁，接入指引的示例用的是通用字段名。

## 看不到用了多少

「用量」页显示你自己的调用量，输入和输出 Token 分开统计。用量在调用结束后 30 秒内更新，所以刚发的请求可能要等一下才出现。

# Topic 4 · 故障排查（用户版）

**可见性：** 管理员与普通用户

## 调用失败时，先看错误码

响应里的 HTTP 状态码和错误码告诉你问题在哪一层。以下是高频问题：

| 错误 | 含义 | 你该做什么 |
|---|---|---|
| `401 invalid_api_key` / `api_key_expired` | 密钥无效或已过期 | 检查是否完整复制（包含创建时显示的前缀）、环境变量是否生效。在「API 密钥」页确认状态；已过期只能新建，不能续期 |
| `403 service_not_authorized` | 你或这个密钥没有该服务的权限 | 确认当前授权、密钥允许服务和服务是否可用；仍无法调用时联系管理员 |
| `429 rate_limit_exceeded` | 超出你在该服务上的调用上限 | 按 `Retry-After` 稍后重试；长期不够用时联系管理员 |
| `503 service_disabled` / `backend_unavailable` | 服务被停用，或当前无法处理请求 | 密钥和配置都不用改，稍后重试。持续失败时把响应里的 Request ID 发给管理员 |
| `404 model_not_found` | Endpoint 或模型名配置错误 | OpenAI SDK、Cursor 等使用「OpenAI 兼容 Endpoint」，Claude Code 使用「Anthropic 兼容 Endpoint」；Claude Code 的 Base URL 误填成带 `/v1` 的地址也能正常调用。API 模型名使用接入指引中的值 |

`/v1/messages` 使用 Anthropic 格式的 `error.type` 分类，例如限流为 `rate_limit_error`；分类名称与下表不同，但对应问题的含义和处理方向相同。

**遇到其他错误，把 Request ID 给管理员。** 每个响应都带 Request ID，管理员可据此查找调用记录并排查原因；部分阶段可能没有数据。普通用户页面不提供逐请求记录——这是权限边界，不是功能缺失。

## 有几件事不是故障

- **用量数字比预期少** —— 用量在调用结束后 30 秒内入账，稍等片刻再刷新页面。
- **看不到完整密钥了** —— 这是设计如此，明文只显示一次。找不到就新建并撤销旧的。

# Topic 4 · 故障排查（管理员版）

**可见性：** 仅管理员。内容为用户版全文 + 以下追加章节。

## 部署失败

失败页给六样东西：失败阶段、原因、已选资源、建议、事件时间、日志入口。先看**失败在第几阶段**——阶段决定了排查方向：

| 失败阶段 | 通常原因 |
|---|---|
| 读取模型信息 | 模型源凭证失效、仓库不存在或无权限。到「系统 → 模型源」更新凭证 |
| 下载模型 / 校验模型文件 | 网络、磁盘空间、或文件摘要不匹配。见下「下载失败」 |
| 校验并预留 GPU | 原来选的卡已被占用或转为异常。进入「等待 GPU 资源」，可等待原 GPU、重新选择 GPU 或取消部署 |
| 加载权重 | 显存不足。可尝试多卡 TP、降低「上下文长度」、调高「显存比例」 |
| 初始化 Runtime / 启动进程 | 运行配置不被该模型支持。检查精度、量化与 Runtime 参数 |
| 健康检查 | 进程起来了但不响应。看日志抽屉里的 ERROR 行 |

**重试会重新确认 GPU。** 「修改配置并重试」保留上次配置供调整，确认后创建新的模型实例，原失败记录和 AI 服务绑定保留，不会自动切换服务。所选 GPU 会重新校验。

## 下载失败分五类，处置完全不同

不要对所有下载失败都点「继续」：

- **网络中断 / 超时 / 限流** —— 临时文件保留，按任务当前提供的「继续」或「重试」恢复下载。
- **凭证失效 / 无权限** —— 继续只会反复失败。先检查「系统 → 模型源」凭证和访问权限，再使用任务提供的重试操作。
- **磁盘空间不足** —— 任务已暂停。先由管理员按运维规范释放足够空间，再按任务可用操作恢复；不要直接改动正在使用的本地模型文件。
- **文件校验失败** —— 任务转为失败且**不会生成本地模型**，避免半损坏的模型被部署。先处理校验失败原因，再用任务的「继续」重新校验。若已生成的受管本地模型后来校验失败，先「重新校验」，仍未通过可「删除文件」后到「下载模型」重新下载。外部目录只能在服务器上修复源目录或恢复路径后重新校验，平台不删除源文件。
- **管理员取消** —— 确认取消前会提示清理临时文件，确认后不能再从当前临时文件继续。

## 实例运行异常

「运行异常」表示健康检查连续失败。平台会自动重启，界面显示「自动重启 1/3」。**自动重启期间 GPU 不会自动释放**；达到重试上限后会转为「运行失败」并释放 GPU。设备消失等异常需要按详情提示处理，不能假设所有异常都会自动恢复。所以看到「运行异常」不要立刻去部署新实例，那几张卡还没回来。

排查顺序：实例详情的「事件」页定位时刻，再在「日志」页查看对应的错误线索。调用问题应结合响应里的 Request ID 查询调用记录；日志和调用记录都不应包含请求或响应正文。

## 监控数据不可用 ≠ 服务故障

指标采集失败时，指标显示 `—` 和最后更新时间，但**服务状态不变**。判断服务能不能用，看状态徽章（依据健康检查），不看指标。这时不要去重启一个本来健康的实例。

另外注意区分三种缺失：`—` 加警告图标是取不到数；`—` 不带图标是「不再适用」（例如已删除用户的最近登录）；`0` 是真实为零。

## 用量对不上

用量按平台转发每次调用时生成的调用记录统计，不依赖监控指标。几种正常情况：

- 流式请求在**流结束时**才入账，进行中的请求不计入；
- 客户端中断的请求按平台已确认的实际 Token 计入——算力确实消耗了；
- 状态为「未知」的记录单列统计，不并入成功也不并入失败。这类记录表示平台重启前没收到最终结果，无法判断成败。
